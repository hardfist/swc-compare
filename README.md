# Rspack SWC Loader Performance Comparison

Conclusion: the performance difference depends on module boundaries and file shape; it cannot be inferred from the SWC version alone. In this uncached full-build benchmark with 2,000 TypeScript modules, `builtin:swc-loader` compared with `swc-loader` has:

- **28.5%** lower typical fresh-process end-to-end time (`1.40x`)
- **34.2%** lower typical compiler lifecycle time after invoking the Rspack API (`1.52x`)
- **36.8%** lower fresh-process peak RSS (211.5 MiB vs 334.8 MiB)
- **29.4%** lower typical time when repeatedly creating a fresh compiler for full builds in a persistent Node.js process (`1.42x`)

The result is different for a single large TypeScript payload. At 64 KiB, the builtin fresh-process build is about 10% faster; at 256 KiB, persistent-process builds are effectively tied. From 1–8 MiB, `swc-loader` is instead about 4–6% faster in the persistent process. However, the external path always has higher peak RSS, growing from `1.10x` at 64 KiB to `1.62x` at 8 MiB.

## Strict SWC Version Alignment

`builtin:swc-loader` does not use the project's installed `@swc/core`; it uses the Rust SWC embedded in Rspack's native binding. This benchmark therefore compares only versions whose underlying SWC crates are fully aligned:

| Component | Pinned version | Underlying version |
| --- | --- | --- |
| `@rspack/core` | `1.7.12` | `swc_core 59.0.1` |
| `@swc/core` | `1.15.21` | `swc_core 59.0.1` |
| `swc-loader` | `0.2.7` | Uses the `@swc/core` version above |

Version evidence: Rspack's [`Cargo.toml`](https://github.com/web-infra-dev/rspack/blob/v1.7.12/Cargo.toml#L139-L141) and [`Cargo.lock`](https://github.com/web-infra-dev/rspack/blob/v1.7.12/Cargo.lock#L5908-L5910), plus SWC v1.15.21's [`swc_core/Cargo.toml`](https://github.com/swc-project/swc/blob/v1.15.21/crates/swc_core/Cargo.toml#L7-L9) and [`Cargo.lock`](https://github.com/swc-project/swc/blob/v1.15.21/Cargo.lock#L5828-L5830). The critical transformation chain is also aligned, including `swc_ecma_codegen 24.0.0`, `swc_ecma_parser 36.0.0`, `swc_ecma_transforms_base 39.0.0`, and `swc_ecma_transforms_typescript 43.0.0`.

Both Rspack configurations are generated by the same factory. A verification script asserts that the loader name is their only difference and rejects `RSPACK_BINDING` or `SWC_BINARY_PATH` overrides of the pinned native binaries. Every build receives a deep clone of the SWC options to prevent Rspack's in-place normalization from leaking across rounds. The SWC configuration explicitly disables `.swcrc`, external configuration files, source maps, and minification, while aligning `disableAllLints`.

## Formal Benchmark Results

Environment: Apple M3 Max (14 logical CPUs), 96 GiB RAM, macOS 26.5.2 arm64, and Node.js 24.19.0. Each group uses 5 warmup rounds followed by 30 measured rounds. Every round alternates AB/BA execution order to reduce ordering and thermal bias. The 95% confidence intervals come from 100,000 paired bootstrap iterations while preserving a 15/15 execution-order quota.

| Scenario | `builtin:swc-loader` median ± MAD | `swc-loader` median ± MAD | Paired external / builtin ratio (95% CI) |
| --- | ---: | ---: | ---: |
| Fresh-process end to end | 208.72 ± 3.64 ms | 290.89 ± 4.19 ms | `1.399x` (1.387–1.413) |
| Compiler lifecycle after invoking the API | 143.57 ± 3.31 ms | 218.60 ± 3.16 ms | `1.519x` (1.505–1.548) |
| Persistent process, fresh compiler full build | 127.18 ± 3.02 ms | 177.84 ± 4.41 ms | `1.416x` (1.388–1.436) |

Fresh-process peak RSS medians are 211.52 ± 1.02 MiB and 334.77 ± 0.72 MiB, respectively, with a paired ratio of `1.583x` (95% CI 1.578–1.589). The builtin path wins 30/30 fresh-process rounds and 27/30 persistent-process rounds. Both final bundles are 10,249,996 bytes and share the same SHA-256:

```text
43dbd7947a1926d0ce101bcfdaf881dab7207528dbd983e06bc4feb84a168402
```

Numeric module IDs incorporate the loader name into the module-identifier hash, which would prevent byte-for-byte comparison even when the bundles differ only in module IDs. This benchmark therefore uses the development mode's default named module IDs for both loaders. This adds no loader-specific configuration and makes direct output-hash verification possible. After timing, the benchmark also executes the bundle and verifies the independently calculated runtime checksum `4287433803`.

## Single Large-File Size Curve

This workload concatenates the same TypeScript AST units used by the many-module fixture into one payload file, plus a fixed 145-byte entry. ASCII whitespace pads the payload to the exact requested byte size. This controls the number of loader invocations, but it represents the generated-code-style shape `concatenated-standard-units-v1`, not every possible large source-file shape.

The test machine is again an Apple M3 Max with 96 GiB RAM running macOS 26.5.2 arm64; this run used Node.js 24.16.0.

All time and RSS ratios below are `external / builtin`. For time, a ratio above 1 means the builtin loader is faster, while a ratio below 1 means the external loader is faster. For RSS, a ratio above 1 means the external loader consumes more memory.

| Payload | Measured rounds | Fresh-process end to end: builtin / external (paired ratio) | Persistent-process full build: builtin / external (paired ratio) | Peak RSS: builtin / external (paired ratio) |
| ---: | ---: | ---: | ---: | ---: |
| 64 KiB | 40 | 71.64 / 79.49 ms (`1.112x`) | 10.68 / 11.31 ms (`1.049x`) | 100.23 / 110.16 MiB (`1.099x`) |
| 256 KiB | 40 | 87.57 / 92.75 ms (`1.063x`) | 26.79 / 27.18 ms (`1.002x`) | 113.70 / 127.74 MiB (`1.121x`) |
| 1 MiB | 25 | 168.24 / 172.54 ms (`1.032x`) | 106.52 / 101.43 ms (`0.957x`) | 150.30 / 186.50 MiB (`1.251x`) |
| 4 MiB | 12 | 681.78 / 679.78 ms (`0.991x`) | 643.40 / 602.22 ms (`0.943x`) | 295.65 / 439.48 MiB (`1.488x`) |
| 8 MiB | 8 | 1547.42 / 1511.92 ms (`0.979x`) | 1547.38 / 1433.21 ms (`0.948x`) | 461.41 / 743.47 MiB (`1.622x`) |

The five sizes use 8/8/6/3/2 warmup rounds, respectively, while retaining the alternating AB/BA order. Here, “fresh process” means that every sample starts a new Node.js process, but the warmed OS page cache remains in place. The 4 MiB and 8 MiB cases are stress tests with fewer samples. Persistent-process measurements repeatedly create compilers inside one Node.js process; they are useful for describing the trend but should not be treated as fully independent experiments.

For every size, the two final bundles pass byte-hash and independently calculated runtime-checksum verification. The generator also records the shape ID, AST unit count, padding size, and payload SHA-256 in the raw results so that results for equal byte sizes but different code shapes are not compared accidentally.

## Workload and Methodology

By default, the generator creates 2,000 deterministic TypeScript modules and one entry that imports them all. Large-file mode reuses the same AST units but concatenates them into one payload. Both modes include interfaces, mapped types, `satisfies`, parameter properties, private fields, optional chaining, nullish coalescing, and object spread, targeting ES2018.

The primary scenario launches a fresh Node.js process for every build, excluding Rspack's persistent cache while retaining the warmed filesystem page cache. It records parent-process spawn-to-exit time, the Rspack API lifecycle, Rspack stats time, and peak RSS. `@rspack/core` is already loaded before API timing begins, whereas `swc-loader` first loads the external `@swc/core` during `compiler.run()`. The API metric is therefore not “pure SWC transformation time.” Fresh-process end-to-end time, which includes the complete startup cost of both paths, is the primary startup result. A second scenario alternates fresh compilers inside one Node.js process while still performing uncached full builds, reducing the influence of first-time native module loading.

`swc-loader` keeps its default asynchronous `@swc/core.transform()` behavior; the benchmark does not change it with `sync: true`. The two stock loaders also have one behavioral difference that ordinary shared configuration cannot remove: with `devtool: false`, the builtin loader disables input source maps, while `swc-loader@0.2.7` overwrites the user-provided `inputSourceMap: false`, causing `@swc/core` to scan for `sourceMappingURL` using its default behavior. The fixture contains no source maps, so this does not affect the output, but the scan remains part of the real `swc-loader` path. This benchmark compares the two stock loaders rather than modified internal microbenchmarks.

[Rspack's architecture documentation](https://www.rspack.dev/api/javascript-api/architecture) explains that builtin loaders run on the Rust side, reducing JavaScript scheduling and cross-language data conversion while making better use of parallelism. These results are consistent with that mechanism. The benchmark uses a synthetic TypeScript graph, so absolute times and speedup ratios will still vary with real project module sizes, plugins, storage, CPUs, and other build stages.

## Why Results Change with File Shape

Ablation experiments support integration paths, rather than SWC version differences, as the most likely source of the gap in the many-module workload. The builtin path invokes Rust SWC directly inside Rspack's Rust loader runner. With `swc-loader`, every module travels through Rspack Rust → Node.js loader runner → `swc-loader` → `@swc/core` N-API → Node.js → Rspack Rust. The latter adds per-module loader-context construction, source and result transfer across boundaries, options JSON serialization, Promise/callback scheduling, and potentially more GC pressure. Matching crate versions still do not guarantee identical native-binary features, allocators, or build settings.

The large-file curve separates this explanation into several parts:

- At 64–256 KiB, external startup adds about 5–8 ms, comparable to the fixed cost of initially loading `@swc/core` and `swc-loader`. As the file grows, SWC transformation and code generation amortize this cost.
- A single payload crosses the loader boundary only once, so the per-module scheduling advantage seen with 2,000 small modules no longer accumulates. The external path's small advantage at 4–8 MiB shows that identical `swc_core` versions do not make the two native binaries equally fast on a large AST. Possible causes include features, allocator choice, LTO, compiler flags, or the surrounding compiler call paths, but the current experiments cannot separate them precisely.
- External-path RSS grows faster with payload size. This is consistent with additional live data from source, results, and N-API async tasks across the JavaScript/native boundary, plus the allocator high-water mark of a second native addon. The extra RSS at 8 MiB is far larger than a few copies of the source text, so it cannot be attributed to a single string copy. The single-file workload also rules out a large Promise queue as the primary explanation for this case.

Additional findings:

- In a separate 20-round ablation with 2,000 modules, the external API path has a paired gap of about 58 ms. Direct loading and preloading experiments jointly estimate that about 5–8 ms (10–13%) comes from the first `require`.
- With total source fixed at 875,663 bytes, a single payload plus entry has nearly identical persistent-process time (81.98 vs 82.00 ms). Splitting it into 500 payload files plus entry changes the result to 37.36 vs 49.41 ms. In the high-file-count range, the combined incremental cost is about 21–22 µs per payload, showing that the main gap accumulates with loader invocations, scheduling, and module lifecycle work.
- In the same independent ablation, first loading the complete external loader in an otherwise idle process adds about 3.8 MiB of fixed RSS, while complete builds differ by about 125 MiB. In a direct SWC experiment, submitting 2,001 asynchronous tasks at once uses about 33 MiB more than limiting concurrency to 16. This supports queued tasks and their retained results/Promises as one possible explanation for part of the memory gap, but it cannot be treated as a direct attribution inside Rspack.

See [Performance Gap Analysis](docs/performance-gap-analysis.md) for the full call chains, source evidence, ablation data, and attribution limits.

## Reproduction

Requires Node.js 20+ and pnpm 11.19.0:

```bash
pnpm install
pnpm verify:versions
pnpm bench
pnpm analyze
```

Quick checks:

```bash
pnpm bench:quick
pnpm bench:large:quick
```

Run the formal 1 MiB single-large-file benchmark or the 4 MiB stress test:

```bash
pnpm bench:large
pnpm analyze

pnpm bench:large:stress
pnpm analyze
```

The scale can also be adjusted with environment variables:

```bash
BENCH_MODULES=5000 BENCH_WARMUPS=5 BENCH_RUNS=30 pnpm bench
BENCH_FIXTURE=large-file BENCH_LARGE_FILE_BYTES=8388608 BENCH_WARMUPS=2 BENCH_RUNS=8 pnpm bench
```

Generated source, bundles, and complete raw samples are stored in `.benchmark-workload/` and are excluded from Git.

GitHub Actions runs both the 500-module and 256 KiB large-file cases on Node.js 20 and 24. Numbers from shared runners are used only to verify version locking, successful builds with both loaders, the result schema, bundle hashes, and runtime checksums; they are not performance gates. Raw results are retained as artifacts for 14 days.
